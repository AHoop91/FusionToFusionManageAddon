# Publish Item: order of operations

This note follows one design through the Publish Item panel, from opening it to the last request sent to Fusion Manage. It says what the code does now, in the order it does it. The last section lists where the order is uneven, as a starting point for clean-up.

Files: the panel is `src/ui/web/publish/js/publish.js` (loading), `publish-mbom.js` (the MBOM dropdown), `publish-bom.js` (the Bill of Materials and the Publish button), `mbom-viewer.js` and `mbom-structure.js` (the structure viewer, section 5) and `publish-jobs.js` (the progress dialog and the Jobs window). Python is `src/publish/panel_sections.py` (the sections), `src/ui/actions/publish_run_actions.py` (starting a run), `src/publish/runner.py` (a run) and `src/publish/sender.py` (the sending).

## 1. Opening the panel: the sections, in order

The panel asks Python for one section at a time (`load_publish_section`) and polls `load_publish_section_status` until it is no longer pending. A section is a slot in `PublishSections`; a slot is read again only when the design, the settings stamp (hub, tenant, workspace), the target or the target id changed, or when the panel forces it. The exception is the read of the whole structure from the Data Model (the long one, and it does not depend on the target): `PublishSections` keeps its rows for the design (and the hub and settings it was read under), so another target re-asks the slot but not the Data Model. The rows go when the panel forces the `structure` section (its refresh button, a finished publish, signing in) or another design is open.

| Step | Section | What it does | Starts when |
| --- | --- | --- | --- |
| 1 | `summary` | Checks the user may publish (`publish_denial`), then reads the design from the Data Model: component id, lineage, item number, file name, description, composition. A design with no item number is refused: it was never published. | The panel opens, another design is open, or Refresh is clicked |
| 2a | `thumbnail` | The design's picture. | The summary is in |
| 2b | `mbom` | Reads the design's record in the Components workspace for its link and asset id, then searches the Items workspace (v1 search) for the items with that lineage id and asset id that are the working version. Each hit is `{id, number, descriptor}`. | The summary is in |
| 3 | The MBOM is chosen | The dropdown shows the descriptors. The panel keeps the chosen number as `target` and the item's id as `target_id` (empty for a new number). It keeps the number it had chosen before when that is still listed, else the first. | The `mbom` answer is in |
| 4 | `structure` | Reads the whole Bill of Materials (every level, once) from the Data Model and marks the lines that cannot be published; the Fusion Manage Bill of Materials is not read here (`mbom_tree` reads it once, 50 levels deep). With a `target_id` the item is read by id; with none the item is searched for by its number while the Data Model is read. | The MBOM is chosen, and asked at the same time as `mbom_tree` when the item has an id (see `mbom_tree` below). If the lookup failed, nothing else is asked: the panel shows why, with a retry. |
| 5 | `properties` | Reads the design's own properties and compares them with the target item (by id when known, else by number). It is shown in the Details Panel. | The structure is in, so it never slows the BOM |

Other things the panel asks for later:

- A new MBOM: the "+" button or the last entry of the dropdown opens a form with the design's item number and a hyphen. `mbom_number` asks whether any item of the workspace already has the number (v3 search on the descriptor, any version). If none, the number is added to the list as a local entry with no id and is chosen. Nothing is made in Fusion Manage until Publish.
- Choosing another MBOM: the Bill of Materials and the properties are cleared and asked for again for the new target (steps 4 and 5), with `mbom_tree` beside step 4; the rows of the Data Model are not read again (they are kept, see above), so only the search for the item, the marking and the two Fusion Manage reads are made again. The thumbnail and the MBOM lookup are kept.
- Details Panel: `component:<id>` and `thumbnail:<id>` for one row.
- `mbom_tree`: the target item's whole Bill of Materials as one tree (`BomService.tree`, `MBOM_DEPTH` = 50 levels, in this one read of Fusion Manage's Bill of Materials; a line at the last level whose own lines exist is marked `cut`), read by the target's id with the working bias; each line has its item id and its line (edge) id. It needs a target id, so a design with no MBOM item is never asked. It raises (rather than leaving a hole) for a line whose parent or child has no item number, a line with no item id, an item inside itself, and a tree of more than 20000 lines; a line at the last level whose own lines the answer shows elsewhere is marked `cut`. It runs only for the structure viewer, and is asked for (`askMbomTree` in `publish.js`, forced, never from a copy) in the same tick as `structure`, from `loadStructure`; the viewer holds its answer until the structure is in, whichever comes first, and keeps its skeleton until both are. A failure is shown in the viewer, whose retry asks for the MBOM alone.

## 2. Clicking Publish (panel)

Publish sends what the structure holds (section 5), not a table: there is no table view any more. `publish()` in `publish-bom.js` asks the viewer for its plan (`ns.mbomViewer.plan()`, which is `ns.mbomPlan.build` in `mbom-plan.js`).

1. The button is off until the structure is built (the structure and the MBOM tree are read) and while the plan has something it cannot publish; its tooltip says what (`problemText`). A click with no plan, or with such a problem, sends nothing.
2. The plan is the job's `items` and `operations`, in the shape the run has always taken (`bom_requests.py` is unchanged): `items` are the design (the root, under the number of the MBOM chosen) and each EBOM component a line of the MBOM was made from, once each; every one goes through the comparison with Fusion Manage, so an item whose properties differ is updated. A bought version or any other added item is never one: it exists already, only its BOM line is added. `operations` come from `structure.changes()` against the MBOM as it was read: an added or moved line is an `add` under its assembly (with the `link` of an added item), a moved line is also a `remove` from the assembly it left, a changed quantity is an `update` (with the line's `edge` and the old quantity), a line that is gone is a `remove`. Removes are listed first, as `bom_requests` sorts them. The BOM line numbers (`sequence`) follow the tree: 1, 2, 3 under an assembly with nothing in Fusion Manage; under one that has lines, those up to the first line that is new, moved in or out of order keep their numbers, and that line and every one after it get numbers above the highest the assembly has had (skipping any a removed or moved-away line holds). A kept line gets a `renumber` (found by its `edge`; a changed quantity goes in the same request, so one line never has two at once), a new one an `add`. Every new number is above all current ones, so the requests of one assembly, which run together, never want the same number, and Fusion Manage lists the lines in the tree's order. Numbers are not kept tidy: a reorder uses numbers above the old ones. The same assembly in two places with the same change is one operation.
3. What it will not publish it says, never drops: `unpublishable` (a line with no item behind it, such as a new manufacturing assembly), `skipped` (a component with no item number, or one whose number Fusion Manage shares: the rules `bomModel.buildItems` still applies to the rows) and `ambiguous` (an assembly in two places with different lines, which have one BOM in Fusion Manage).
4. `start_publish` carries the job (`summary` with the target's item number, `root_number`, `items`, `operations`) and the settings stamp.

## 3. Starting the run (Python, Fusion's thread, then a worker)

1. Fusion's thread: `HubContexts.attempt` (hub, tenant, connection, workspace, sign-in together). It refuses when no Items workspace is set, when the stamp is not the one now active (settings changed since the design was read), or when no model id is open.
2. A worker thread: the permission check again (a page may have been open while permissions changed).
3. `PublishFolder` is made in the temp folder, `PublishRun` is created with `send=True` and put on the `JobQueue`. The panel opens its progress dialog on the run and polls `list_publish_jobs`.

## 4. The run (the queue's worker thread)

The run uses clients tied to its cancel token, so Cancel ends a request at once. `PublishRun._steps` does the following, by stage.

**Validating**

1. Items whose item number is shared (`shared_numbers`, from the panel's summary of components) are taken out as unpublishable.
2. `ReadAhead` starts, for the rest of the items: the Data Model reads (several components to a request, 3 in flight) and the Fusion Manage searches by item number (v3, working version, 10 numbers to a search, 2 in flight).
3. The sections of the workspace's fields are read in the background.
4. `_require_unique_numbers` waits for every search. If a number is carried by several Fusion Manage items, the whole run fails with nothing written (`SharedItemNumbers`). A failed search fails the run too.

**Items** (5 at a time)

For each item (`_prepare`, then `_item`):

1. Skipped if it has no number or its number is shared.
2. `_compare`: the lookup (`lookup_item`, from the shared search hits) and the Data Model read run together, then `compare_with_item` gives the state (`new`, `found`, `multiple`, `unknown`) and the rows.
3. `_component`: the Components item to link, from the Data Model's link. A component the Data Model does not link is recorded as failed (no search of the picklist), and the item is sent without the link. With a link, the pivot of the linking field is read for the linked item (`GET /api/v3/workspaces/<items ws>/views/1/pivots/<field>?pivotItemId=<id>`, `PivotService`): the derived fields it lists (`COMPONENT_ASSET_URN`, `COMPONENT_LINEAGE_URN`) are sent with the link, each in the section the pivot names. Fusion Manage refuses a create without them. A pivot that cannot be read fails the link.
4. `_option_rows`: picklist text becomes option links, numbers are fitted to the field's digits. A value with no option is left out and recorded.
5. `_request`: the thumbnail is downloaded (a fresh signed url is asked for if it expired) and `item_request` makes a POST (new) or PATCH (found) request. Nothing is made for a found item that already matches, except the thumbnail.
6. The request is written to the item's folder, and the item's state and id go to the manifest.
7. The dispatcher learns the item's id, then `send_item` sends the request: skipped if the send log says it was done, a create that was cut off is looked up by number first, a create is logged as intended before it is sent, and a refusal is logged. At most 5 writes are in flight across everything.

A failure in one item never stops the others.

**Bill of Materials**

1. `_write_boms` writes each parent's requests to `bom/<parent>.bom.request.json`.
2. After every item is sent, `_send_boms` sends each parent's requests, 5 parents at a time. For a parent, the removals and updates go first, then the additions, 5 requests at a time. Each request holds markers for item ids, versions and the tenant. The dispatcher fills them: an id it learned, else a search by item number (`WORKING`), which must find exactly one. A parent whose create failed is not sent. A failed request ends its step; the other parents go on.
3. A duplicate line is not an error, nor is a line already gone after a cut-off send.

**End**

The manifest is saved (`root`, workspace, tenant, model, cancelled) and the phase becomes `done`, `error` or `cancelled`. A run with failed rows is announced with a message box unless a progress dialog is following it. A failed run is retried from its folder (`SendRun`): it sends the written requests again, skips what the send log holds, and refuses when the tenant is not the one it was made for.

## 5. The structure viewer (what Publish sends)

The Bill of Materials pane is the structure viewer (`#pub-structure`) and nothing else: the Table view and its switch are gone. `#pub-bom` is only a notice area beside it (bouncing balls with "Checking for existing Bill of Materials in Fusion Manage..." while the MBOM lookup is on its way, then a message, an error or the choice of the MBOM when several were found); `viewer.show(true)` hides it and `viewer.showTable()` (kept under its old name) shows it. The loading is three steps, each drawn once, so nothing goes back to an earlier one: the balls (summary read, MBOM lookup asked), the list of the MBOMs found when there are several, then the viewer's own skeleton (the toolbar, not usable yet, and the two tables with grey rows, `ui.skeletonRows`) from the moment the MBOM is known until the structure is built; `publish.js` opens it (`viewer.show(true)`) in `answerMbom` and `chooseTarget`, and the line under it (`viewer.say`: reading the Fusion Component structure, with how many lines so far, then, when only the MBOM is still awaited, reading the Fusion Manage Bill of Materials) is the one place that says what it waits for. The footer has no count of items: the lines say what is happening. There are no pills (words in coloured boxes) on a line: a change shows as a coloured bar at the left of the MBOM line, a check mark at the right of an EBOM line says it is all in the MBOM (green; blue when a purchased part stands for it), and a line with more to say has an icon button beside its quantity (`noteButton`) that opens its note under the row (`noteRow`; the same words are its tooltip, one line each, which goes as soon as the pointer leaves the button). The notes are made in `ebomNotes` ("Linked to purchased part X", "Qty 6 exceeds 4 in the EBOM", "Qty 2 of 4 is in the MBOM", not under the same assembly) and `mbomNotes` ("Purchased part for X", "New line", "Moved from X", "Quantity changed from a to b", "Moved within its assembly", not in the EBOM); a warning (amber) is for quantities that do not agree. An open note is kept until the structure is read again. Edits in the viewer are dropped when the Bill of Materials is read again (another MBOM, Refresh, a finished publish). Publish sends the plan of the structure (section 2).

What it does when opened (`ns.mbomViewer.refresh`): waits for the structure (step 4, the whole tree) to make the EBOM and, if the MBOM item has an id, for the `mbom_tree` answer, which the panel asked for at the same time as the structure, and maps each line to an EBOM line by item number (`mapByNumber`: for a number that is in the EBOM more than once, the line under the same EBOM assembly first); a design with no MBOM item starts as a copy of the EBOM. Then `ns.mbomStructure.create` holds the MBOM and every edit goes through it (move by drag or by the Add to assembly action, which lists the MBOM as a tree of places, add from the EBOM by drag, add existing items with the Add Items picker, quantity, remove, undo and redo). A refused edit says its reason in a toast (there is no red line above the panes). Adding an EBOM line the MBOM holds some of adds what is left of its quantity (4 in the EBOM and 1 in the MBOM adds 3): to its line under the same assembly when there is one (that line goes from 1 to 4, and is published as a quantity update), else as a line of its own; with none left it is refused. Phantoms are off (`phantom: false`) until Settings name the Type field and its Phantom value. Any line of the MBOM takes lines dropped in the middle of it, a part the design has no lines for included (manufacturing may build a BOM for it); the top and bottom quarter of a line mean before and after it. Drag and drop is made from mouse events (`pointerDown`, `pointerMove`, `pointerUp`), not the browser's own drag and drop, which Fusion's embedded browser does not carry through (`products/js/sortable.js` is pointer-based for the same reason; it only reorders one flat list, so the tree drag, with its into/before/after zones and the drop across panes, is its own).

Not done: new manufacturing assemblies and phantoms (refused), Settings for the phantom fields, and properties or where-used for a line. The table code is gone (`bom-table.js`, `bom-filters.js`, `bom-columns.js`, `bom-cells.js` and `bom-plan.js` were deleted); `pubUi.foldTools` in `ui.js` is the viewer's Collapse and Expand all. `bomTree.setTop`, `setKids` and `unloaded` are still there, but only their tests call them. Nothing here has written to a tenant yet: the first run should use a scratch MBOM number and review `bom/<parent>.bom.request.json` in the run's folder before sending.

### The dialog: a new manufacturing item, and a bought version

Backend: `src/publish/bought_items.py` (`BoughtItems`), `src/ui/actions/item_create_actions.py` (the actions below). Front end: `src/ui/web/publish/js/item-panel.js` (`ns.pubItemPanel`), `css/item-panel.css`, built on the shared `ns.formControls` ([workspace-forms.md](workspace-forms.md)).

**The dialog.** It opens as a modal over the page (Escape, the close button or a click outside closes it; not while a save runs). Two entry points in `mbom-viewer.js`: the toolbar icon button Create New Manufacturing Item (the box with a plus; `open({mode: 'assembly'})`) and, on a Fusion Component (EBOM, left) line below the root, the row action Create bought version (`open({mode: 'bought', sourceNumber, number})`; an MBOM line has no such action, and the existing Create assembly button, a local edit of the structure, is unchanged). It asks `items_form` or `bought_open`, draws each section of the form as a card that folds (`ns.section.make`, from `section.js`; a refused or invalid field unfolds its section), with every field stacked (label over control, required fields starred, a description as an info icon), puts the copied `values` into the controls, shows what the add-in sets (`locked`: the bought number, Make or buy, the source link) read only with the value it will have, in the field's own section, and starts a section folded when the workspace folds it (unless it holds a required field). Save checks the form in the browser (`collect`), sends `items_create` or `bought_create`, and is off while the request runs, as are Close and Cancel (one click makes one item; a rebuilt structure does not close a dialog that is saving). A refusal keeps every value typed, shows each `fields` message under its field and the `message` (with the messages of fields the form does not hold, such as the number of a bought version) in the line at the top. A saved item is told in the dialog with its number ("Item MFG-1-B was created in Fusion Manage."); the structure is not changed and no node is added, so the item is brought in with Add existing part. When `can_create` is false Save is off with the reason. The Create bought version action is not shown on a component line that is in the MBOM already (the line has an MBOM line made from it), and it is off, with the reason as its tooltip, until Make or buy is set up in Settings (nothing is asked of Fusion Manage when the structure opens: a component with no item, or one with a bought version, is found by the dialog when the action is used; a component with no item is told there, as the `bought_open` error): the `summary` section carries `make_buy` (true when the Items workspace's five Make or buy settings are all set), which `publish.js` hands the viewer as `boughtReady`. Not seen in Fusion: nothing here was run in it. Nothing here writes a bill of materials: only the item is created (one `POST /api/v3/workspaces/<ws>/items`), so a bought item has no children. A PLM default that creates a BOM when the item enters a workflow cannot be tested here. The bought dialog is opened with one request, `bought_open` (with a loader), which looks for a bought version and reads the form together (see the Rules): one found is offered with Use existing item, which adds it to the MBOM (`onFound`) without making another. A saved bought version, or a chosen existing one, is added to the MBOM (the right pane) by `createBought` in `mbom-viewer.js`: `structure.addItems` with `source` set to the EBOM line's key, so it stands for that line, in that line's quantity, inside the selected assembly or at the end; it is a line to publish like any other. A manufacturing item made from the toolbar is not added.

**Quick add.** The last toolbar button (an arrow into a bar) makes the MBOM a copy of the EBOM: `structure.matchEbom()` replaces every line under the MBOM with the EBOM lines and what is under them, with the same item numbers and quantities, as one step of the history (Undo gives the old lines back). When the MBOM has lines already, `matchEbom` in `mbom-viewer.js` first asks with `ns.pubItemPanel.confirm` ("Are you sure you want to override Fusion Manage?"; the dialog opens on Cancel); with none it matches at once. Nothing is sent until Publish. A line Fusion Manage has with the same item number under the same assembly stays that line (`matchEbom` merges by number, level by level: its line id, number and the lines under it are kept; the EBOM gives the order and the quantity); the lines the EBOM does not have show as removed, and the EBOM lines Fusion Manage does not have as new. Seen live: copying the whole EBOM as new lines removed each sub-assembly's line and added it again, and the adds under it clashed with the lines its own bill of materials already had. So the plan also never adds a line to an item whose bill of materials in Fusion Manage already holds it (`held` from `structure.changes()`; only its quantity is brought in step), and a line removed and added again keeps the number and line id of the one it replaces (`identity`), so its requests name the line. The button is off, with the reason, when the EBOM has no lines. Not seen in Fusion.

**Line numbers of the MBOM.** The number shown on a line of the right pane is its BOM item number (`itemNumber`) in Fusion Manage, and the lines are in that order (`build_tree` sorts by it: the answer lists the edges by id, not by number; seen live: edges 5522, 5524, 5525, 5528 held numbers 1, 2, 8, 3). An assembly with no change keeps the numbers it has (1, 2, 3, 8 stay). An assembly with a new, moved or reordered line is numbered 1, 2, 3 in the tree's order and the pane shows those numbers, which are what `mbom-plan.js` sends (`ns.mbomPlan.lineNumbers` gives both the viewer and the plan the same numbers). A request body holds `itemNumber` as a whole number; the example seen live holds it as text (`"5"`), which Fusion Manage accepts either way is not known. **Automatic renumber** (the last toolbar button) asks first (`ns.pubItemPanel.confirm`), then marks every assembly that has a line of Fusion Manage's whose number is not its place (`structure.renumber()`, the `renumber` flag, one undoable step; none to mark says so in a toast), so the pane shows 1, 2, 3 and the publish sends them.

**Set Position.** Every line of the MBOM below the root has a hover action Set Position (an arrow up and an arrow down). It opens a small box (`openPositionBox` in `mbom-viewer.js`, the same popover slot as Add to assembly) holding the number the line shows and "New position number": any whole number from 1, with no upper limit (10 with three lines is fine). `structure.setNumber(id, value, current)` gives the line that number (`pin`), keeps the numbers the other lines of its assembly show (`current`, from `ns.mbomPlan.lineNumbers`, pinned the same way) and puts the lines in the order of their numbers; one undoable step. A value that is not a whole number is refused (`bad_number`), and one another line has too (`number_taken`): both are said in the box, which stays open. The publish keeps pinned numbers: an assembly with a pinned line is not numbered 1, 2, 3; each line takes its pin, else the number it has when that is above the one before it, else the one above the one before it (`numbering` in `mbom-plan.js`). A line moved to another assembly or dragged loses its pin, and Automatic Renumber lets all pins go. Not seen in Fusion.

**Split Quantity.** Every MBOM line below the root has a hover action Split Quantity (one line branching in two), disabled with a tooltip when its quantity is 1 or less. It opens one box (`openSplitBox`, on the shared value box `openValueBox` that Set Position also uses) with "Quantity to move" (above 0 and less than the line's quantity) and the tree of the MBOM to choose the assembly in, with a search above it (`destTree`, the same tree as Add to assembly, which also shows each line's number from the top down: 3.1 is the first line of line 3; the line, what is under it and the assembly it is in cannot be chosen), and a Split button. `structure.split(id, parentId, amount)` takes the amount off the line and gives it to the chosen assembly: as a new line (a copy with no line id, `isNew`, and none of what is under it, as an item's own lines are the same wherever it is used) or, when that assembly already has the same item, by adding it to that line. The assembly must not be the line's own (`split_same_assembly`) or inside it (`inside_itself`); a quantity that takes it all is `split_too_much`. One undoable step. `compare()` counts an EBOM line over every MBOM line made from it, in every assembly, so a split keeps it matched, more than the EBOM has is `exceeded`, and `addFromEbom` adds only what is left. Not seen in Fusion.

**Settings** (`WorkspaceConfig.make_buy`, Items kind, part of the configuration file and its transfer): `field` (the Make or buy field, a picklist), `make_value` and `buy_value` (the **links** of two of its options, `/api/v3/lookups/...`, compared by link), `source_field` (a field that links to one item, filled with the source) and `suffix` (letters, numbers, `.`, `_`, `-`; up to 20 characters). Nothing is known to the code: no field id is written in it. The feature is off until all five are chosen; a half-chosen set is a settings problem (`MakeBuyConfig.problems`), as are equal values, a value that is not an option link, and a field also used as another mapped, component or default field (`_filled_twice`). `source_field` being a linking field and both values being options of `field` are checked when the form is read, not on save (`BoughtItems._check_make_buy`: a message that says what to change). `save_settings` refuses a hub member who changes it (see [permissions.md](permissions.md)).

**Actions** (token and `items_status` poll, as `products_*`; picker options from `search_options`/`search_status`). Each answer is `{token, pending, ok, result, message, fields}`; a refusal has `message` and, when Fusion Manage or the add-in names fields, `fields: {field id: message}`.

| Action | Request | `result` |
| --- | --- | --- |
| `items_form` | `{kind: "assembly"}` | `{form, locked: {field id: text}, number_field, can_create}`: the Items form, the number a required text field, Make or buy (set to Make when set up) in `locked`: in its section, shown, never sent |
| `items_create` | `{values}` | `{id, link, number}`. Make or buy is set to Make whatever `values` hold. A missing or taken number is refused beside `number_field`. |
| `bought_open` | `{source_number}` (the EBOM line's number; or `{source_id}`) | one of: `{found: {id, link, number, name, url}}` (`url`: its page in Fusion Manage), the bought version of that item there is already (a bought one whose source link names the source: `BoughtItems._bought_rows`, `_found`; the `CONTAINS` filter on the source link field is not seen live), which the dialog offers ("... already exists ... Use it in the MBOM?", button Use existing item, then `onFound`, `addBought`); or `{form, number, values: {field id: value}, locked: {field id: text}, number_field, source_id, can_create}`: `form` holds what the person may change (what `plan_copy` skips is left out) and, locked, the number, Make or buy, the source link and the component link (shown "None"); `values` is copied from the source in the form's shapes; `number` is source number + suffix; `source_id` is the item the form was made from, which the dialog sends with `bought_create`. A failure is shown in the dialog with Try again. |
| `bought_create` | `{source_id}` (the dialog sends the one `bought_open` answered; `{source_number}` is still taken, and searched for), and `values` | `{id, link, number}`. The number, Make or buy (Buy) and the source link are set by the add-in, whatever `values` hold. |


**Rules** for a bought version: the source is given by its id (digits only) or by its item number. the Data Model's link of a component is not used: `lifecycle.itemUrn` is the design's Components record, not the Items workspace item (`dev/manufacturing-data-model.md`), so `bought_open` finds the item by its number: `BoughtItems._source` uses `ItemFinder.search` (working version) and `resolve_hits`, and continues as for that id. **Not known:** whether the id the search finds is the working version (the v3 search names the working version); the item is read by that id, so the dialog's number and values are those of the item at that id. `bought_open` reads the item, the form and three searches together once the id is known (the number taken, the items whose number contains the source's, and the bought versions), starts the searches that need the item number with the number the page sent and makes them again when the item has another; a bought version found is answered before anything is refused (a source that is bought, a number that is too long or taken, an item made from the source under another number). A failed read of any of them is raised, not taken as none. `bought_create` does not trust the form: it takes the `source_id` the dialog sends (else it searches again), reads the item and checks again under the lock. no hit is refused (the number is not in Fusion Manage yet: publish it first), several hits are refused (the number is shared). Both or neither of the two is refused by `bought_create` (`bought_open` takes the id when both are given: the number is then only what the page expects). A source that already holds `buy_value` is refused (a bought item is not made); Make or empty, an item never classified, is allowed; the number is rebuilt from the source's number, and refused when it is longer than the number field's limit (when the form knows one), when `number_taken` says it exists (v3 search, whatever the version), or when a v1 search of items whose number contains the source's number finds one whose source link names the source (a bought version made under another suffix). Checking and creating run under one lock per (workspace, number), so two creations in this process make one item. The search indexes lag a little, and an item made by hand with no number containing the source's, linked to it, is not found: limits, not guarantees. `plan_copy` skips (each with a `reason` in the user's language) what is not chosen on the form: the number, Make or buy, the source link, the component link, and pictures. A picture is copied as it is: `create_bought` reads the source's picture (`load_image`, the same read the Item panel uses) and sends it as a data uri with the create, unless Settings leave the field out; one that cannot be read refuses the create (`app.bought_picture_unreadable`). `make_buy.skip_fields` (Settings, Items card, "Fields to copy": a checklist by section of the form, each field ticked unless left out) names fields that are also not copied; empty means every field the form holds. `WorkspaceService._place` gives each field of the Items workspace its `section` and `section_order` for that list. A checkbox read as the text `true` or `false` is understood as ticked or not. Fields the form leaves out (hidden, computed, never edited) are never copied (`plan_copy` does not write a second filter). Revisions: a bought item is a new item with its own revisions; the source link holds the source item as it was when the bought item was made, and nothing keeps them in step. **Not seen live**: the v1 filter `CONTAINS` on the number field, a date held as `YYYY-MM-DD` in an item read, the item number field being writable when the form shows it as `info`, and a refusal of an item `POST` (see [validation.md](validation.md)).

## 6. Where the order is uneven

These are facts from reading the code, not decisions.

1. **Two ways of finding the item.** The panel finds the target by lineage and asset id (`mbom`) and reads it by id. The run does not carry the id: it finds each item again by item number (`ReadAhead`, `lookup_item`, `Dispatcher._item_id`, `_created_before`). An item renumbered in Fusion Manage is compared correctly in the panel, but Publish searches for the old number and treats the item as new or fails to find it.
2. **The same search twice.** Step 4 (`structure`, or `tree`) searches Fusion Manage for the design's number when there is no id, and the run's `ReadAhead` searches for it again. The panel's result is not handed to the run.
3. **The new-number check is not the run's.** `mbom_number` asks whether the number is free when the form is submitted. The run checks uniqueness only as "not more than one", so a number taken after the check is treated as an existing item and updated.
4. **Children are matched by number only.** The run's items for child assemblies have no lineage or asset search.
5. **A design with no MBOM found.** `mbom` answers with an empty list, no target is set, and the panel compares and publishes under the design's own item number, searched by number. That is the old behaviour, kept beside the lineage search: a design whose item has no lineage or asset id filled in is found only this way.

**Where a publish spends its time (seen in the log, 7 items, 6 BOM operations, about 15 s).** Looking up the item numbers 2.5 to 3.4 s (one Data Model read of about 1.5 s and one search); preparing the items about 5 s (each `PATCH` of an item takes about 1.2 s, five at a time, so seven items take two rounds); then the Bill of Materials. In the Bill of Materials stage each request that names an item's revision (`{{version:...}}`) reads that item (about 0.9 s, 44 KB). `Dispatcher._item_facts` made that read while holding the lock, so every read waited for the one before it (seven items took about 7 s). It now reads outside the lock, and `_read_facts` reads the items of a request together (`FACT_READERS`, 5 at a time). What remains is the time of the requests themselves (0.4 to 1.2 s each). Not measured after the change.
